# Импорт Monefy

Все методы `/api/imports/monefy` требуют `Authorization: Bearer <access token>`.
Импорт доступен пользователю без собственных счетов (включая удалённые),
созданных категорий, членства в счетах и связанных транзакций. Скрытые
категории учитываются. Общий каталог других пользователей не мешает импорту.

## Последовательность запросов

1. `GET /api/imports/monefy/availability` возвращает
   `{"available": true, "reasons": []}`. Причины отказа: `owned_accounts`,
   `created_categories`, `account_membership`, `transactions`.
2. `POST /api/imports/monefy/preview` принимает **тело одного SQLite .db**
   с `Content-Type: application/octet-stream`. Multipart и CSV не принимаются.
   Ответ `201` содержит предпросмотр. До выбора типов счетов подтверждение
   блокируется диагностикой `target_account_kind`.
3. `POST /api/imports/monefy/{previewID}/options` принимает JSON:

   ```json
   {"account_kinds": {"source-account-id": "spending"}}
   ```

   Нужно передать каждый исходный счёт ровно один раз. Допустимы `spending`,
   `deposit`, `investment`. Ответ `201` — **новый** `preview_id` с выбранными
   параметрами и заново проверенным каталогом. Показывайте пользователю этот
   ответ и подтверждайте именно новый ID. Прежний preview неизменяем.
4. `POST /api/imports/monefy/{previewID}/confirm` принимает JSON:

   ```json
   {"acknowledge_exclusions": true}
   ```

   Флаг подтверждает все исключения именно этого preview. При отсутствии
   исключений можно передать `{}`. Наличие `blocking` запрещает импорт при
   любом значении флага. Файл, суммы и параметры в confirm не передаются;
   неизвестные поля запроса отклоняются.

Успешный confirm возвращает `200` с `preview_id`, `completed_at` и счётчиками
`accounts`, `categories` (новые), `reused_categories`, `transactions` (обычные),
`transfers`. Повторный и конкурентный confirm возвращают тот же результат,
в том числе после удаления файла предпросмотра и перезапуска сервера.

## Предпросмотр

Ответ содержит:

- `preview_id`, `sha256` исходного файла, `expires_at` в RFC3339;
- `can_confirm`: нет блокирующих диагностик; при
  `requires_exclusion_confirmation: true` дополнительно нужно согласие;
- `counts`: количество счетов, категорий, обычных операций и переводов;
- `period_from`, `period_to`: первая и последняя дата операций/переводов,
  `null` для пустой истории;
- `currencies`: валюты импортируемых счетов;
- `accounts`: `source_id`, `name`, `currency`, `kind`, `icon`, `source_icon`,
  `initial_balance`, `initial_balance_date`, `final_balance`,
  `source_included_in_total`, `source_disabled_at`;
- `categories`: `source_id`, `name`, `type`, `icon`, `source_icon`,
  `source_disabled_at`, необязательный `existing_id`;
- `diagnostics`: `severity`, `code`, `entity`, `source_id`, `message`;
- `exclusions`: `entity`, `source_id`, `reason` для каждой исключённой живой
  записи, связанной с удалённой сущностью;
- `deleted`: число удалённых исходных записей по таблицам.

Все денежные значения — **десятичные строки**, например `"-1234.567"`.
Не преобразовывайте их в двоичный float для сохранения или сравнения.
Итоговые балансы учитывают начальные остатки, операции и обе стороны переводов.
При блокирующих ошибках итоги являются предварительными.

Категории сопоставляются по типу и имени после удаления крайних пробелов и
приведения к нижнему регистру. Несколько совпадений в источнике или серверном
каталоге блокируют импорт; `existing_id: "ambiguous"` обозначает такую
неоднозначность каталога и не является UUID. Совпавшие записи переиспользуются
без изменения имени, иконки, создателя или настроек видимости. Если каталог
изменился после preview, нужен новый запрос options или новая загрузка.

## Сохранение смысла данных

Новые счета личные, владелец имеет долю 100%. Каждая операция и каждый перевод
получают `transaction_shares` на полную сумму списания/операции. Перевод — одна
запись с `amount` и `to_amount`; начальный остаток записывается только на счёте.

Иконки Monefy автоматически не сопоставляются. Новые счета получают стандартную
иконку `preset:debit-card`, новые категории — `preset:other`. В options можно передать
`category_icons`: отображение source ID новой категории в выбранную иконку
`preset:<id>` или `preset:<id>|<цвет>|<цвет рамки либо none>`. Выбор сохраняется
в новом предпросмотре и при импорте; пропущенные параметры сохраняют прежний выбор.
Изменение иконок переиспользуемых категорий через импорт запрещено.
`IsIncludedInTotalBalance` и `disabled` не преобразуются автоматически:
счета создаются активными, поведение общего баланса определяется выбранным
типом. История отключённых сущностей сохраняется; исходные флаги и даты
отключения явно показываются вместе с предупреждением `target_flags`.
Удалённые сущности не восстанавливаются.

Блокирующие ограничения назначения: имя длиннее 100 символов, нулевая обычная
операция, сумма вне диапазона `NUMERIC(15,4)` (не более `99999999999.999` по
модулю для исходных тысячных), операция до календарной даты начального остатка.
Даты записываются в календарные DATE без сдвига часового пояса; время суток
истории не входит в модель транзакций co-wallet. Остальные правила источника
описаны в [контракте парсера](../../importer/monefy/README.md).

## Ошибки и ограничения

Тело ошибки: `{"error":"stable_code"}`. Низкоуровневые ошибки SQL и финансовые
данные не включаются в ответы об ошибке или журналы.

| HTTP | Код / причина |
| --- | --- |
| 400 | `invalid_request`, `invalid_account_kinds`, `invalid_category_icons`, `preview_blocked`, `exclusions_not_confirmed`, `source_*` (коды парсера) |
| 401 | Нет действующей авторизации |
| 404 | `preview_not_found`: чужой, истёкший, отсутствующий или некорректный ID |
| 408 | `request_timeout` |
| 409 | `account_not_empty`, `catalog_changed`, `preview_stale`, `import_busy`, `preview_storage_full` (нет места после очистки своих старых файлов), `import_conflict` |
| 413 | `upload_too_large` |
| 415 | `expected_sqlite_binary` |
| 500 | `internal_error`; импорт не считается подтверждённым, запрос можно повторить |

Файл — до 64 MiB, JSON параметров — до 2 MiB, не более двух одновременно
работающих парсеров на сервер. Обработка preview/confirm имеет контекст
10 секунд, сетевое чтение ограничено серверным `ReadTimeout` 15 секунд.
Парсер не исполняет SQL из файла, расширения и пользовательские объекты схемы;
его приватная SQLite-копия удаляется после чтения даже при ошибке.

## Хранение и конкурентность

Нормализованные данные и параметры хранятся до 24 часов в
`IMPORT_PREVIEW_DIR`; по умолчанию это `cowallet-import-previews` внутри
системного временного каталога. Docker монтирует отдельный volume
`import_previews` в `/var/lib/cowallet/import-previews`. Каталог имеет права
0700, файлы — 0600. Настройка параметров не продлевает срок хранения.
Файл удаляется после успешного confirm. Очистка просроченных файлов выполняется
при запуске, перед записью и раз в минуту. При сбое удаления её повторит
периодическая очистка; результат уже завершённого импорта остаётся успешным.

Лимиты: 5 preview на пользователя, 128 MiB на нормализованный файл,
512 MiB суммарно для сохранённых файлов. Новый preview вытесняет старые
preview того же пользователя при достижении лимита количества или размера.
Файлы других пользователей не вытесняются. Запись сначала готовится во временном
файле (до 128 MiB сверх общей квоты), поэтому ошибка записи не удаляет старые
предпросмотры. Для вытесненного preview нужно загрузить файл заново; квитанции
завершённых импортов остаются в БД, повтор подтверждения не создаёт дубликаты.
При нехватке места из-за файлов других пользователей дождитесь очистки по TTL или обратитесь к администратору. Хранилище рассчитано на **один процесс backend**; несколько
пишущих реплик с общим volume не поддерживаются. Удаление volume отменяет
незавершённые preview, но не затрагивает импортированные данные.

В PostgreSQL сохраняется только квитанция завершения (ID, пользователь,
счётчики, время), вместе с импортированными сущностями в одной транзакции.
Перед повторной проверкой пустоты блокируется строка пользователя FOR UPDATE.
Она конфликтует с KEY SHARE, который существующие внешние ключи берут при
обычном создании счетов, категорий, транзакций и членства. Проверка выполняется
отдельным запросом после получения блокировки и видит завершившиеся записи.
Обычная операция, начавшая запись после захвата блокировки импортом, может
завершиться после него — это последовательность «импорт, затем операция».
Каталог блокируется FOR SHARE на время сопоставления и записи; новые конфликты
имён приводят к полному откату и необходимости обновить preview.
